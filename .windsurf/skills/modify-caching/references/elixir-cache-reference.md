# elixir_cache Library Reference

Source: https://github.com/MikaAK/elixir_cache

The goal of this library is to unify Cache APIs and make adapters easy to implement and sharable across all storage types. Testing is a first-class concern — caches are isolated per test and don't leak state.

## Cache Behaviour

```elixir
@callback child_spec({cache_name :: atom, cache_opts :: Keyword.t()}) :: Supervisor.child_spec()
@callback opts_definition() :: Keyword.t()
@callback start_link(cache_opts :: Keyword.t()) :: {:ok, pid()} | {:error, term()} | :ignore
@callback put(cache_name :: atom, key :: atom | String.t(), ttl :: pos_integer, value :: any) :: :ok | ErrorMessage.t()
@callback put(cache_name :: atom, key :: atom | String.t(), ttl :: pos_integer, value :: any, Keyword.t()) :: :ok | ErrorMessage.t()
@callback get(cache_name :: atom, key :: atom | String.t()) :: ErrorMessage.t_res(any)
@callback get(cache_name :: atom, key :: atom | String.t(), Keyword.t()) :: ErrorMessage.t_res(any)
@callback delete(cache_name :: atom, key :: atom | String.t(), opts :: Keyword.t()) :: :ok | ErrorMessage.t()
@callback delete(cache_name :: atom, key :: atom | String.t()) :: :ok | ErrorMessage.t()
```

## Available Adapters

| Adapter | Description |
|---------|-------------|
| `Cache.Agent` | Simple agent-based caching |
| `Cache.DETS` | Disk-persisted caching with Erlang DETS |
| `Cache.ETS` | High-performance in-memory cache with ETS |
| `Cache.Redis` | Redis adapter using Redix & Poolboy, supports Redis JSON and Redis Hashes |
| `Cache.ConCache` | Wrapper around the ConCache library |
| `Cache.PersistentTerm` | Extremely fast reads via `:persistent_term`, no TTL support, best for rarely-written config |
| `Cache.Counter` | Lock-free atomic integer counters via `:counters`, stores refs in `:persistent_term` |
| `Cache.Sandbox` | Test adapter (auto-selected when `sandbox?: true`) |

Some adapters inject adapter-specific functions into your cache module via `__using__/1`. For example, `Cache.Redis` adds hash and pipeline functions, `Cache.ETS` adds the full set of ETS operations listed below, and `Cache.Counter` adds `increment/1,2` and `decrement/1,2`.

## `use Cache` Macro

When you `use Cache`, the following is generated:

**Required options:**
- `adapter` — one of the adapters above (required)
- `name` — atom cache name (required)

**Optional:**
- `sandbox?` — if true, uses `Cache.Sandbox` adapter for test isolation
- `opts` — adapter options, can be:
  - Keyword list (validated against adapter's `opts_definition/0`)
  - `{module, function, args}` — MFA tuple
  - `{application_name, key}` — Application env lookup
  - `application_name` — Application env lookup with module as key
  - Zero-arity function

**Generated functions:**
- `cache_name/0` — returns the cache name atom
- `cache_adapter/0` — returns the adapter module
- `adapter_options/0` — resolves and returns adapter options
- `child_spec/1` — for supervision tree
- `put/2`, `put/3` — store value with optional TTL
- `get/1` — retrieve value (returns `{:ok, value}` or `{:ok, nil}`)
- `delete/1` — remove key
- `get_or_create/2` — get or compute and store

Values are automatically encoded/decoded via `Cache.TermEncoder` (binary term format with optional compression).

## Starting Caches

In your `application.ex`:

```elixir
children = [
  {Cache, [MyModule]}
]
```

## Runtime Configuration

Adapter options can be resolved at runtime:

```elixir
# MFA tuple
use Cache, adapter: Cache.Redis, name: :my_cache, opts: {MyModule, :opts, []}

# Zero-arity function
use Cache, adapter: Cache.Redis, name: :my_cache, opts: &MyModule.opts/0

# Application config: Application.fetch_env!(:my_app, MyModule)
use Cache, adapter: Cache.Redis, name: :my_cache, opts: :my_app

# Application config with key: Application.fetch_env!(:my_app, :cache_opts)
use Cache, adapter: Cache.Redis, name: :my_cache, opts: {:my_app, :cache_opts}
```

## Cache.ETS Adapter

**Options** (NimbleOptions):
- `write_concurrency: boolean | :auto` — enable write concurrency (`:auto` supported)
- `read_concurrency: boolean` — enable read concurrency
- `decentralized_counters: boolean` — use decentralized counters
- `type: :set | :bag | :duplicate_bag` (default `:set`)
- `compressed: boolean` — enable ETS compression
- `rehydration_path: string` — persist ETS to disk on exit and rehydrate on startup

**Error handling:** The ETS adapter's `get/3`, `put/5`, and `delete/3` all rescue exceptions and return `{:error, ErrorMessage.internal_server_error(...)}` instead of crashing.

**Additional ETS functions** generated by `use Cache` with ETS adapter:
- `all/0`, `delete_table/0`, `delete_all_objects/0`, `delete_object/1`
- `first/0`, `last/0`, `next/1`, `prev/1`
- `first_lookup/0`, `last_lookup/0`, `next_lookup/1`, `prev_lookup/1` (OTP 26+)
- `lookup/1`, `lookup_element/2`, `lookup_element/3` (OTP 26+), `member/1`
- `insert_raw/1`, `insert_new/1`
- `match_pattern/1`, `match_pattern/2`, `match_delete/1`
- `match_object/1`, `match_object/2`, `match/1`
- `match_spec_compile/1`, `match_spec_run/2`
- `select/1`, `select/2`, `select_count/1`, `select_delete/1`, `select_replace/1`
- `select_reverse/1`, `select_reverse/2`
- `foldl/2`, `foldr/2`
- `update_counter/2`, `update_counter/3`, `update_element/2`, `update_element/3` (OTP 26+)
- `tab2list/0`, `tab2file/1`, `tab2file/2`, `tabfile_info/1`, `file2tab/1`, `file2tab/2`
- `info/0`, `info/1`, `table/0`, `table/1`, `take/1`, `whereis/0`
- `to_dets/1`, `from_dets/1`
- `safe_fixtable/1`, `rename/1`, `give_away/2`, `setopts/1`, `slot/1`
- `init_table/1`, `repair_continuation/2`, `test_ms/2`, `is_compiled_ms/1`

**ETS rehydration:** When `rehydration_path` is set, the adapter traps exit signals (SIGTERM, SIGHUP, SIGQUIT, etc.) and writes the table to disk via `tab2file`. On startup, it attempts to rehydrate from the file. If the file has a different table name or is corrupt, a fresh table is created.

## Cache.PersistentTerm Adapter

Backed by Erlang's `:persistent_term` storage. Extremely fast reads, expensive writes/deletes. Best for configuration values or data that changes infrequently.

- **No TTL support** — values persist until explicitly deleted
- Uses `{cache_name, key}` tuples as persistent_term keys
- All operations rescue exceptions and return `{:error, ErrorMessage.internal_server_error(...)}`

```elixir
defmodule MyApp.ConfigCache do
  use Cache,
    adapter: Cache.PersistentTerm,
    name: :config_cache,
    opts: []
end
```

## Cache.Counter Adapter

Atomic integer counter adapter backed by Erlang's `:counters` module. Counter references and key-to-index maps are stored in `:persistent_term` for zero-latency access.

**Options** (NimbleOptions):
- `initial_size: pos_integer` (default `16`) — initial number of counter slots to pre-allocate

**Behaviour:**
- `put/4` accepts only `1` or `-1` as values (increment/decrement). Other values return an error.
- `get/2` returns the current integer value, or `nil` if the key is unknown.
- `delete/2` removes the key from the index map and zeroes the counter slot.

**Injected functions** (via `use Cache`):
- `increment/1`, `increment/2` — atomically increment by step (default 1)
- `decrement/1`, `decrement/2` — atomically decrement by step (default 1)

```elixir
defmodule MyApp.HitCounter do
  use Cache,
    adapter: Cache.Counter,
    name: :hit_counter,
    opts: [initial_size: 32]
end

MyApp.HitCounter.increment(:page_views)
MyApp.HitCounter.decrement(:active_users)
{:ok, count} = MyApp.HitCounter.get(:page_views)
```

## Strategy Adapters

`Cache.Strategy` is a behaviour for strategy-based adapters that compose over existing cache adapters. Strategies receive the underlying adapter module and its resolved opts so they can delegate operations appropriately.

Strategies are specified using the tuple format:

```elixir
use Cache,
  adapter: {StrategyModule, UnderlyingAdapterOrConfig},
  name: :my_cache,
  opts: []
```

### Cache.Strategy Behaviour

```elixir
@callback opts_definition() :: Keyword.t()
@callback child_spec({cache_name :: atom, strategy_config :: term, adapter_opts :: Keyword.t()}) :: Supervisor.child_spec()
@callback get(cache_name :: atom, key :: atom | String.t(), strategy_config :: term, adapter_opts :: Keyword.t()) :: ErrorMessage.t_res(any)
@callback put(cache_name :: atom, key :: atom | String.t(), ttl :: pos_integer | nil, value :: any, strategy_config :: term, adapter_opts :: Keyword.t()) :: :ok | ErrorMessage.t()
@callback delete(cache_name :: atom, key :: atom | String.t(), strategy_config :: term, adapter_opts :: Keyword.t()) :: :ok | ErrorMessage.t()
```

### Cache.HashRing

Consistent hash ring strategy using `libring`. Distributes keys across Erlang cluster nodes via `:erpc` (or configurable `rpc_module`).

**Options:**
- `ring_opts: keyword` — options passed to `HashRing.Worker` (e.g. `node_blacklist`, `node_whitelist`)
- `node_weight: pos_integer` (default `128`) — virtual nodes per node on the ring
- `rpc_module: atom` (default `:erpc`) — module for remote calls (must implement `call/4`)
- `ring_history_size: pos_integer` (default `3`) — previous ring snapshots kept for read-repair

**How it works:**
1. Key is hashed to determine the owning node via the consistent ring
2. Local node → execute directly; remote node → forward via `rpc_module`
3. Ring tracks node membership automatically via `HashRing.Managed` with `monitor_nodes: true`

**Read-repair:** On a `get` miss, previous ring snapshots (maintained by `Cache.HashRing.RingMonitor`) are consulted. On a hit from an old node, the value is migrated to the current owner and deleted from the old node asynchronously.

```elixir
defmodule MyApp.DistributedCache do
  use Cache,
    adapter: {Cache.HashRing, Cache.ETS},
    name: :distributed_cache,
    opts: [read_concurrency: true, ring_history_size: 5]
end
```

> When `sandbox?: true`, the ring is bypassed and all operations execute locally against the sandbox adapter.

### Cache.MultiLayer

Cascades reads and writes through multiple cache layers (e.g. ETS → Redis).

**Read behaviour:** Layers are iterated fastest → slowest (list order). On a hit from layer N, the value is backfilled into layers 1..N-1.

**Write behaviour:** Layers are written slowest → fastest (reverse list order). If a slow write fails, the write stops and returns an error.

**Options:**
- `on_fetch: mfa | fun/1` — optional callback invoked on total cache miss
- `backfill_ttl: pos_integer | nil` — TTL for backfilled entries (default `nil`)

Layers can be:
- A cache module (already running, not supervised by this adapter)
- An adapter module (e.g. `Cache.ETS`) — auto-started and supervised
- A tuple `{AdapterModule, opts}` — adapter with inline opts

```elixir
defmodule MyApp.LayeredCache do
  use Cache,
    adapter: {Cache.MultiLayer, [Cache.ETS, MyApp.RedisCache]},
    name: :layered_cache,
    opts: [on_fetch: &__MODULE__.fetch/1]

  def fetch(key) do
    {:ok, "value_for_#{key}"}
  end
end
```

### Cache.RefreshAhead

Proactively refreshes hot keys in the background before their TTL expires.

**Options:**
- `refresh_before: pos_integer` (required) — milliseconds before TTL expiry to trigger refresh
- `on_refresh: mfa | fun/1` — optional refresh callback (if not provided, cache module must define `refresh/1`)
- `lock_node_whitelist: atom | [atom]` — optional node whitelist for distributed refresh locks

**How it works:**
1. `put/5` wraps the value as `{value, inserted_at_ms, ttl_ms}` before delegating
2. `get/4` unwraps and checks if `now - inserted_at >= ttl - refresh_before`; if so, spawns async refresh
3. Per-cache ETS deduplication table prevents concurrent refresh tasks for the same key
4. `:global` distributed locking prevents redundant refreshes across nodes

```elixir
defmodule MyApp.Cache do
  use Cache,
    adapter: {Cache.RefreshAhead, Cache.Redis},
    name: :my_cache,
    opts: [
      uri: "redis://localhost:6379",
      refresh_before: :timer.seconds(30)
    ]

  def refresh(key) do
    {:ok, fetch_fresh_value(key)}
  end
end
```

> When `sandbox?: true`, values are stored unwrapped and refresh logic is bypassed entirely.

## Cache.get_or_create/3

```elixir
Cache.get_or_create(MyCache, "user:123", fn ->
  case UserRepo.get(123) do
    nil -> {:error, ErrorMessage.not_found("User not found")}
    user -> {:ok, user}
  end
end)
```

Pattern: get from cache → if nil, call function → if `{:ok, value}`, store and return.

## Telemetry Events

- `[:elixir_cache, :cache, :put]` — span
- `[:elixir_cache, :cache, :get]` — span
- `[:elixir_cache, :cache, :get, :miss]` — counter on cache miss
- `[:elixir_cache, :cache, :delete]` — span
- `[:elixir_cache, :cache, :put, :error]` — counter on error
- `[:elixir_cache, :cache, :get, :error]` — counter on error
- `[:elixir_cache, :cache, :delete, :error]` — counter on error

All events include `%{cache_name: cache_name}` metadata.

## Sandbox Testing

When `sandbox?: true`:
- The `Cache.Sandbox` adapter is used automatically (a simple Agent cache unique to the root process)
- Keys are prefixed with a sandbox ID from `Cache.SandboxRegistry`
- Each test process gets isolated cache keys

**Setup required** in `test/test_helper.exs`:

```elixir
Cache.SandboxRegistry.start_link()
ExUnit.start()
```

Then in each test's `setup`:

```elixir
Cache.SandboxRegistry.start([MyCache, OtherCache])
```

### ETS Sandbox Compatibility

`Cache.Sandbox` implements all ETS-specific operations so that caches using `Cache.ETS` as their adapter work transparently in tests when `sandbox?: true`. This includes:

- **Navigation:** `first/0`, `last/0`, `next/1`, `prev/1`
- **Lookup:** `lookup/1`, `lookup_element/2,3,4`, `member/1`
- **Insert:** `insert_raw/1`, `insert_new/1`
- **Pattern matching:** `match_pattern/1,2`, `match_object/1,2`, `match_delete/1`
- **Select:** `select/1,2`, `select_count/1`, `select_delete/1`, `select_replace/1`
- **Fold:** `foldl/2`, `foldr/2`
- **Counters:** `update_counter/2,3,4`
- **Table ops:** `tab2list/0`, `info/0,1`, `take/1`, `slot/1`, `safe_fixtable/1`, `init_table/1`
- **Unsupported in sandbox:** `to_dets/1`, `from_dets/1`, `to_ets/0,1` — return `{:error, :not_supported_in_sandbox}`

> **Note:** Match spec guards are not evaluated in the sandbox. If you rely on guards in match specs, test against the real adapter.

### Cache.CaseTemplate

Reusable ExUnit case template for projects with many test files. Define a `CacheCase` module once, then `use` it in any test file for automatic sandboxed cache setup.

**Defining a CacheCase:**

```elixir
defmodule MyApp.CacheCase do
  use Cache.CaseTemplate, default_caches: [MyApp.UserCache, MyApp.SessionCache]
end
```

Or discover caches from a running supervisor:

```elixir
defmodule MyApp.CacheCase do
  use Cache.CaseTemplate, supervisors: [MyApp.Supervisor]
end
```

**Using in a test file:**

```elixir
defmodule MyApp.SomeTest do
  use ExUnit.Case, async: true
  use MyApp.CacheCase

  # or with additional caches just for this file:
  use MyApp.CacheCase, caches: [MyApp.ExtraCache]
end
```

**Options for `use Cache.CaseTemplate`:**
- `default_caches` — list of cache modules to start for every test
- `supervisors` — list of supervisor atoms; their `Cache` children are discovered at runtime

**Options for `use MyApp.CacheCase`:**
- `caches` — additional cache modules for this test file only
- `sleep` — milliseconds to sleep after starting caches (default `10`)

Detects duplicate cache registrations at setup time and raises with a descriptive message.

## Creating Custom Adapters

Implement the `@behaviour Cache` callbacks:

```elixir
put(cache_name, key, ttl, value, opts \\ [])
get(cache_name, key, opts \\ [])
delete(cache_name, key, opts \\ [])
opts_definition()  # NimbleOptions definition
child_spec({cache_name, cache_opts})
```

If the adapter exports `__using__/1`, it will be invoked to inject adapter-specific functions into the cache module.
